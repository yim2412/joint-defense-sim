# 적이 없어서 0이었다

> 합동 통합방어 시뮬레이터 · 2026-09-05 · [`1efbaa8`](https://github.com/yim2412/joint-defense-sim/commit/1efbaa8) → [`5deed92`](https://github.com/yim2412/joint-defense-sim/commit/5deed92)

레이저를 종결했다. 함정용 지향성 에너지 무기를 v17.2 에 만들어 두고 오래 방치했다가,
"이 기능이 실제로 뭔가 하긴 하는가"를 재는 트랙에서 마지막으로 판정한 것이다.

측정은 깔끔했다. 3개 시나리오를 돌렸고 숫자가 전부 0 이었다.

```
무인기 군집 포화 / 항만 침투 복합 / 연안 포화 공격
→ 레이저 격추 0.00 · 아군 피격 0.00 · 함정 손실 0.00
```

**아군 피격이 0.00 이다.** 무인기가 떼로 몰려오는 시나리오에서 아군이 한 대도 안
맞았다. 그때 나는 이걸 *"레이저가 없어도 함대가 멀쩡하다"* 로 읽었다. 그래서
**음성 확정 종결**로 커밋했다 — 툴팁에 "켜도 안 바뀌는 이유"를 적고, 로드맵에서 빼고,
메모리에 재시도 금지를 못 박았다.

## 다음 세션에서 뒤집혔다

프로브 설정을 다시 보다가 한 줄이 없는 것을 봤다.

```python
cfg = {..., 'enemy_fleet_preset': '무인기 군집 포화', ...}
#            enemy_fleet_mode='preset' 이 없다
```

`enemy_fleet_mode` 가 없으면 프리셋 이름을 읽지 않는다. **적 편대가 생성되지 않았다.**

그러니까 아군 피격 0.00 은 레이저와 아무 상관이 없었다. **적이 없었다.**
위협이 0 이면 피격도 0 이고 손실도 0 이고 레이저 격추도 당연히 0 이다.
모든 지표가 0 인 화면을 보면서 나는 그중 하나만 골라 기능의 성질이라고 읽었다.

적이 실재하는 조건에서 다시 쟀다.

| | 오판 측정 | 재측정 |
|---|---|---|
| 총 위협 | **0** | 32 |
| 요격률 | — | 0.410 |
| 아군 피격 | 0.00 | **1.16** |
| 레이저 격추 | 0.00 | **0.00** |

**판정 자체는 살아남았다.** 적이 실재해도 레이저 격추는 여전히 0 이고 ON/OFF 가
완전히 같았다 — 드론이 5km 교전권에 들어오기 전에 함포가 23km 에서 다 잡는다.
그래서 종결은 유지하고 **근거 수치만 유효한 값으로 갈아 끼웠다.**

결론이 안 바뀌었다는 게 이 건의 무서운 점이다. 판정이 맞았기 때문에,
**측정이 무효였다는 사실은 영영 안 드러날 수도 있었다.**

## 같은 유형을 다음 주에 또 만났다

죽은 토글 43개를 전수로 돌리는 스캐너를 만들었다. 지상 BMD 자산 6개가
**북한 탄도탄 40발이 날아오는 시나리오에서도 델타 0** 이 나왔다. 이번엔 이상하게
여기고 발사 조건을 역추적했다.

```python
# engine_combat.py — 발사 조건은 토글이 아니라 재고를 본다
ground_inv = {'ashore_sm3': cfg.get('ashore_sm3_stock', 0), ...}
if ground_inv[key] > 0:   # ← 여기서 막혔다
```

UI 는 체크박스를 켜면 **재고를 자동으로 부여한다**(24/24/16/32/16).
스캐너는 `enable_ashore` 같은 토글만 켜고 **재고를 0 으로 뒀다.**
발사가 원천 차단된 상태에서 "발사가 0 회니 죽은 기능"이라고 읽고 있었다.

토글과 재고를 짝으로 준 뒤 121초 만에 다섯 개가 전부 살아났다.

```
ashore_sm3_fired +18 · thaad +24 · lsam +4 · chungung +12 · patriot +14
```

**두 건의 구조가 같다.** 프로브 설정이 실제 실행 경로를 재현하지 못했고,
그 결과 나온 0 을 기능의 성질로 읽었다.

## 세 번째는 방향이 반대였다

한 세션이 새 아키텍처를 검증하다 두 건을 실패로 보고했다 — 정밀 교전이 한 번도
안 걸리고(`n_precise=0`), 병렬 실행이 프로세스 풀 붕괴로 죽는다고.

다음 세션이 별도 스크립트로 다시 쟀더니 둘 다 멀쩡했다.

| 보고된 실패 | 실제 원인 |
|---|---|
| `n_precise = 0` | 프로브가 **오타 난 프리셋 이름**을 써서 그 경로에 안 들어감 |
| `BrokenProcessPool` | 테스트 스크립트에 **`if __name__ == '__main__'` 가드가 없음** |

앞의 둘은 측정이 기능을 죽었다고 만들었고, 이건 측정이 기능을 고장 났다고 만들었다.
**셋 다 코드는 멀쩡했고 코드를 재는 쪽이 틀렸다.**

## 진단법을 나에게도 적용해야 했다

이 트랙에는 "기능이 효과 없어 보일 때 기능을 의심하기 전에 볼 것" 이라는 4단계
진단법이 있었다. 첫 항목이 이거다.

> **경쟁 경로가 이 기능의 표적을 가로채는가?**

극초음속 활공을 재측정할 때 이 진단법을 적용해서, 과거 측정이 **지상 방어 계층을 끈
채** 이뤄졌다는 걸 찾아냈다. 고도가 결과를 바꾸려면 고도별로 교전창이 열리고 닫히는
층이 있어야 하는데, 그 층을 꺼 놓고 "고도는 영향이 없다"고 결론지었던 것이다.
켜고 다시 재니 요격률이 **0.610 → 0.718** 로 올라갔다.

그런데 문서에 이렇게 적혀 있다.

> ⚠ 이 트랙의 1차 재측정도 **똑같은 함정에 빠졌다가**, 진단법을 스스로에게 적용해
> 잡아냈다.

진단법을 만들어 놓고, 그 진단법으로 남의 측정을 고치면서, **내 측정에는 안 걸었다.**

## 처방 — 측정을 무효로 만드는 조건을 코드가 알게 했다

세 개를 넣었고, 셋 다 "조심하자"가 아니라 실행 가능한 것이다.

```python
# ① 위협이 0인 측정은 결과가 아니라 무효다
if total_threats == 0:
    raise AssertionError('측정 무효 — 적 편대가 생성되지 않았다')

# ② 프로브 cfg 를 손으로 조립하지 않는다
from audit_verify_regression import _BASE   # 실제 실행 경로와 같은 기반

# ③ 토글에는 짝이 있다 — 재고·짝 기능까지 UI 와 동일하게
_BMD_GROUND = {'enable_ashore': {'ashore_sm3_stock': 24}, ...}
```

①이 핵심이다. **음성 결과를 낼 때 "측정이 유효했는가"를 사람이 기억해서 묻는 게
아니라, 무효인 측정이 결과를 내지 못하게** 만들었다.

## 이 건에서 남긴 규칙

> **모든 지표가 0 인 화면을 보면, 기능이 0 을 만들었는지 무대가 0 이었는지부터 가른다.**
> 둘은 화면에서 똑같이 생겼다.

그리고 하나 더. 이 셋 중 두 건은 **커밋한 뒤에** 뒤집혔고, 한 건은 결론이 안 바뀌어서
하마터면 안 뒤집힐 뻔했다.

> **측정 코드도 코드다.** 기능에 회귀·정적 검사·게이트를 걸면서, 그 기능을 재는
> 코드에는 아무 검사도 걸지 않고 있었다. 판정을 내리는 쪽이 검증이 더 얇았다.
