> (고쳐야 한다면 그 이유를 커밋 메시지에 남긴다 — 규약이 틀린 것인지,

## 0. 목적 — 이 분석은 무엇을 위한 것인가

**전체 파악을 통해 "무엇을 어떤 순서로 고칠 것인가"를 정하는 것.**

이 목적이 모든 판단의 기준이다.

- 산출물의 정본은 **발견 대장(`FINDINGS.md`)** 하나다. 축별 분석 문서는 근거 보관용 부산물이다.
- 분석 문서의 두께는 성과가 아니다. **고칠 목록의 질**이 성과다.
- 이 목적에 맞지 않는 축은 얕게 넘긴다. 축 분할이 코드베이스와 안 맞으면 그렇게 말하고 다시 짠다.

## 1. 공통 규약 — 모든 판에 적용

### 1.1 근거 등급 (모든 주장에 필수)

| 등급 | 의미 | 결론에 쓸 수 있나 |
|------|------|-------------------|
| `[실측]` | 실제로 돌려서 출력을 본 것 | 가능 |
| `[코드]` | 코드를 읽고 논증한 것 (파일:라인 + 앵커 필수) | 가능 |
| `[추정]` | 근거가 불완전한 것 | **불가** — TOP 목록에 올리지 않는다 |
| `[미확인]` | 확인하려 했으나 못 한 것 + 왜 못 했는지 | 불가 (그대로 남긴다) |

- `[실측]`은 **명령과 출력을 그대로** 붙인다. 요약해 옮기면 그 순간 `[추정]`이다.
- 확인 못 한 것을 확인한 것처럼 쓰지 않는다. 모르면 `[미확인]`.
- 근거 없는 칭찬·일반론 금지. 좋게 써주지 않는다. 틀린 건 틀렸다고 한다.

### 1.2 인용 형식 — 앵커 텍스트 의무

라인 번호만으로는 코드가 바뀌면 엉뚱한 곳을 가리킨다.

```
engine_combat.py:3421 `if pk_base * ecm_factor > rand():`
```

- 파일:라인 **+ 그 줄의 원문 한 조각(앵커)** 을 함께 적는다.
- 검사 스크립트가 앵커가 해당 라인에 실제로 있는지 대조한다.
- 코드가 바뀌어 앵커가 안 맞으면 `라인 이동됨` 으로 표시만 하고 **자동 갱신하지 않는다.**
  그 발견이 아직 유효한지는 사람이 판단할 일이다.

### 1.3 시점 고정

- 모든 산출물 첫 줄에 분석 기준 커밋 해시(`git rev-parse HEAD`)를 박는다.
- 인용한 파일:라인은 그 시점 기준임을 명시한다.

### 1.4 차분 — 이미 아는 것을 또 발견하지 않는다

시작 전에 `감사보고서.md` · `plan_roadmap.md` · 메모리의 막다른길 기록을 읽는다.

발견마다 이력 표시:

| 표시 | 의미 |
|------|------|
| `[기존]` | 이미 알려진 것 |
| `[재발]` | 고쳤는데 되살아난 것 |
| `[신규]` | 처음 나온 것 |

- 이미 **음성 결론**이 난 접근(대잠 EMCON 튜닝·레이저 효능 등)을 다시 제안하지 않는다.
- 기존 감사가 놓친 축이 무엇인지도 밝힌다. **그게 이 분석의 진짜 가치다.**

### 1.5 편향 차단

- 각 판은 이전 산출물의 **사실**(파일·수치·목록)만 이어받는다.
  이전 판의 **판정·결론**은 재검토 대상으로 본다.
- 이전 결론과 충돌하는 증거를 만나면 숨기지 말고 명시하고, 어느 쪽이 맞는지 다시 판정한다.

### 1.6 분석과 수정의 분리

- **분석 판에서는 코드를 고치지 않는다.** 한 줄짜리 자명한 버그도 대장에만 올린다.
  (코드가 바뀌면 커버리지 표와 인용 라인이 흔들리고 기준 해시가 무의미해진다.)
- 예외: 분석을 막는 것(스크립트가 안 돌아감)만 고치고, 그 사실을 기록한다.
- 수정은 분석이 끝난 뒤 **별도 판**에서. 그때 대장의 묶음 순서를 따른다. → 9절(B단계)

### 1.7 판 운영

- **한 판 = 하나의 축 = 하나의 산출물.** 축을 합치지 않는다.
- 발견이 나올 때마다 **즉시** `FINDINGS.md`에 flush 한다. 판 끝에 몰아 쓰지 않는다
  (그때는 이미 앞부분 기억이 흐리다).
- 판이 길어져 중간 요약이 발생했으면 산출물에 기록한다:
  *"이 판은 중간 요약이 발생했다 — 후반 발견의 신뢰도가 낮을 수 있음."*
- 판 시작 시 **이번 판에서 무엇을 어떤 순서로 볼지 3~5줄로 먼저 제시**한다.
  사용자가 방향을 틀 기회를 준다(동의를 기다리지는 않는다).
- 판 중간에 예상과 다른 것이 나오면 즉시 보고하고 계획 변경 여부를 말한다.
  **조용히 방향을 바꾸지 않는다.**

### 2.0 0단계 — 지형 + 사각 지도 + 캘리브레이션

세 가지를 한다. **분석하지 않고, 무엇을 분석할지 정하는 판이다.**

**(a) 지형**

- 폴더 전체 파일 표화: 경로·라인수·최종수정일·역할. 라인수는 실제로 센다 `[실측]`.
- 분류: 런타임 코드 / 도구·스크립트 / 문서 / 산출물 / 죽은 것으로 보이는 것.
- 총 코드 라인수 = 분석 규모의 기준선.
- `CLAUDE.md` 파일구조표·README와 실제 파일 목록의 불일치를 전부 잡는다.
- `COVERAGE.md`를 생성 — 모든 파일을 `안봄` 상태로 초기화.

**(b) 사각 지도** — 기존 도구가 이미 잡는 걸 다시 훑는 건 낭비다. 다만 **제외가 아니라 두 겹으로**:

| 영역 | 처리 |
|------|------|
| 기존 도구가 커버한다고 **주장**하는 영역 | 전수 재훑기 금지. 표본 3~5건으로 **도구가 실제로 잡는지** 확인 |
| 표본에서 하나라도 샌 영역 | 커버 안 된 것으로 보고 **전수**로 전환 |
| 도구가 아예 안 보는 영역 | 처음부터 전수 |

`audit_static_scan.py` · 회귀 골든 · pre-commit 게이트가 무엇을 검사하는지 코드에서 추출해 목록화한다.

**(c) 탐색 품질 캘리브레이션** — 정지 규칙보다 **먼저** 해야 한다.

- `감사보고서.md`와 `git log`에서 **과거에 실제로 발견됐던 결함** 5~10건을 뽑는다.
- 그 결함이 있던 시점 기준으로, **내 분석 방법이 그걸 잡아내는지** 확인한다.
- 잡는 비율을 기록한다 — 이게 **이번 분석 결과를 얼마나 믿을지의 근거**다.
- 못 잡으면 방법이 약한 것이다. **정지 규칙(5절)을 적용할 자격이 없다.**

> 이게 없으면 "발견 0건"을 성과로 보고할 수 있다. 실제로는 못 찾은 건데.
> 발견 수는 *코드가 깨끗하다* 와 *내가 대충 봤다* 를 구분하지 못한다.

### 2.1 1단계 — 뼈대

1. 실제 import를 **스크립트로** 전부 추출해 의존 그래프 복원 `[실측]`.
   (눈으로 고르면 한 줄 다중 import를 놓친다 — 실측 33/47 전례)
2. `CLAUDE.md`가 선언한 단방향 계층이 실제로 지켜지는지 대조. 위반은 파일:라인+앵커.
3. 순환 의존 실검사 — 있으면 사이클 경로를 그대로 출력.
4. cfg 값 하나를 골라 end-to-end 추적:
   UI 체크박스 → cfg 빌드 → 엔진 진입 → 틱 루프 → stats → MC 3경로 → 결과탭.
   중간에 끊기거나 유실되는 지점을 찾는다.
5. 재할당 전역(`global X`) 전수 grep → 각각이 이름 import 되는 곳이 있는지 대조.
   **이 프로젝트가 두 번 당한 부류다** (`_GLOBAL_POOL`, `CHART_DPI`).
   → 2026-09-20 `chk_global_name_import` 로 도구화됨. 이 판에서는 **도구가 맞게 보는지**를 본다.
6. **전역 상태 오염** — 전역 DB(`ENEMY_DB`·`FRIENDLY_DB`·`SHIP_DB`)를 `.copy()` 없이
   참조 후 mutate / `cfg = dict(cfg)` 미복사. MC 반복 간 상태가 새는 자리.
7. **기능 간 의존(짝) 지도** — 어느 토글이 어느 토글이 켜져 있어야 의미가 있나.
   *레이더 침묵은 회피 기동이 OFF면 죽는다* 부류를 **발견하는** 절차가 A에 없었다
   (B에는 `짝:` 필드가 있는데 A에 그걸 찾는 판이 없으면 채울 내용이 안 나온다).
8. **순회 필터 정합** — 잘못된 객체가 잘못된 경로로 들어가는가
   (CAP기가 대잠 순회에 진입해 공대공 무장을 어뢰로 조회 → KeyError, v18.01.16).
9. **cfg 키 오타·부모 무수정** — `enable_xxx` 문자열 오타는 조용히 무시된다 ·
   `BattleEngine` 상속이 `TimeStepEngine` 시그니처·훅 기본인자 동작을 바꾸지 않는가.

### 2.2 2단계 — 모델 타당성

**내적 일관성과 외부 대조를 분리한다.**

**A. 내적 일관성 `[코드]`**

- 물리 수식 전수 표화(탐지·RCS·소나·대기·지형·침수·연료·유도).
  각각: 무슨 근사인가 / 어떤 가정이 깔렸나 / 그 가정이 깨지는 조건은.
- 확률 합성이 수학적으로 옳은지: 독립 가정 남용, 이중 계산, 순서 의존, `[0,1]` 이탈.
  Pk 체인을 손으로 따라가 검산한다.
- 단위가 경계를 넘을 때 일관한지(km↔m, kts↔마하, s↔ms, USD raw↔`/1e6`).

**B. 외부 대조 `[실측]` 또는 `[미확인]`**

- DB 수치를 공개 제원과 대조. **출처 URL을 반드시 단다.**
- 출처를 못 찾으면 `[미확인]`으로 남긴다. **기억으로 쓰지 않는다.**
- 동급 무기끼리의 정합(같은 계열인데 속도가 다르다 등) 이상치. **변경분이 아니라 전수.**
- **DB 테이블 간 키 정합** — 한 테이블에 있는 개체가 다른 테이블에 없어 **조용히 0**이 되는가.
  (054B형이 `ENEMY_SHIP_SAM_LOADOUT`에 없어 SAM·CIWS **0발** → *"054A보다 강한 발전형"* 이
  실제 교전에선 054A보다 약한 **정체성 역전**, v18.04.06) · `normalize_enemy_db` 누락 필드.
- **재고·편성 규모 현실성** — 제원이 맞아도 *양*이 틀리면 결과가 뒤집힌다.
  아군 VLS 셀 수·미사일 재고가 실제 탑재량과 정합하는가(재고 과다 = 비현실적 압도) ·
  적 편대가 실제 교리(다축 대량 동시 포화)와 맞는가. **정밀무기 1발 편성은 비현실**이고,
  실제로 *'포화'인데 6발* 인 프리셋이 있었다(`7c04561`).

**C. 왜곡의 크기 `[실측]`**

- 각 근사가 결과를 어느 방향으로 미는지 논증하고, **크기는 ON/OFF MC를 실제로 돌려** 수치로 낸다.
- 못 돌리는 항목은 `미측정` 으로 명시. **추정치를 적지 않는다.**
- **효과가 0으로 나오면 거기서 멈추지 않는다.** 왜 0인지를 묻는다 —
  무대가 없는가(레이저 v17.2) / 짝 기능이 OFF인가(레이더 침묵) / 게이트 버그인가.

**D. 지표·집계 정의의 정합 `[코드]`** — *이 축이 통째로 빠져 있었다*

물리 수식이 맞아도 **무엇을 세고 무엇을 안 세는지**가 어긋나면 결과가 거짓말을 한다.
이 프로젝트에서 실제로 두 번 터진 자리이고, 하나는 지금도 **v22 1순위**다.

- **분자와 분모가 같은 모집단인가.** `intercepted_threats`는 `MissileObj`만 세는데
  `total_threats`에 자폭 플랫폼을 넣으면 *"때리는데 분모엔 있고 막아도 분자엔 없는"* 위협이
  생긴다 — **한쪽만 고치는 게 안 고치는 것보다 나빴다**(`be4e8b9`, 되돌림).
- **분모가 통제되는가.** 항모가 함재기를 무한 생산하면 위협 수가 편성에 따라 폭주해
  요격률 비교 자체가 성립하지 않는다(편대 추천 역순 — [[project-fleet-metric-flaw]]).
- **이중 계산**(`enemy_ships_destroyed` 와 격추 집계가 겹치는가) · 파생 지표의 정의 일관성.

### 2.3 3단계 — 검증 체계 자체

0. **도구가 언제 도는지부터 본다.** 훅에 물린 것과 *사람이 기억해야 도는 것*을 가른다 —
   "메웠다"고 선언된 사각이 수동 도구에 걸려 있으면 **실행되지 않는 한 메운 게 아니다.**
1. `audit_static_scan.py` · `audit_verify_regression.py`를 실제로 돌리고 출력을 그대로 붙인다 `[실측]`.
2. 회귀 골든이 커버하는 것 / 못 하는 것을 표로. 골든에 반영 안 된 신기능 = 회귀 사각.
3. **아무것도 검증하지 않으면서 통과하는** 테스트·감사 코드를 찾는다. 특히:
   - 기본값끼리 비교해 **배선이 끊겨도 참인** 단언
   - 보호 장치를 재면서 *"막지 않았으면 무엇이 일어났을지"* 를 단언하지 않는 것
4. 찾았으면 **실제로 일부러 깨뜨려** 통과하는지 확인한다 `[실측]`.
5. `audit_effect.py` 효과 프로브가 실제로 효과를 재는지, `EFFECT_DEBT` 유예 현황.
6. **결정론** — `sim_seed` 키를 실제로 쓰는가 · 신규 `random`/`numpy.random` 호출이
   RNG 소비 순서를 바꿔 골든을 흔드는가(같은 seed → 같은 결과인지 2회 실행 대조).

### 2.4 4단계 — 부채·안정성·성능

1. 죽은 코드(호출처 0)·중복 구현·매직 넘버를 **스크립트로 전수 추출** `[실측]`.
2. NaN/Inf · 0나눗셈 · 음수 log/sqrt · 빈 리스트 평균 · 확률 clamp 누락 grep 후
   **각 히트를 실제로 읽어 참/거짓 판정**. grep 히트 수만 세지 않는다.
3. 예외 삼킴(`except: pass`) · subprocess 인코딩 누락으로 신호가 사라지는 자리.
4. 성능은 추정하지 말고 **cProfile로 실측** `[실측]`. 단발 1회 + 캠페인 1회, 상위 20 함수.
   추측한 병목과 실측 병목이 다르면 그 차이를 명시한다.
   **wall-time 회귀 가드**: 기준값 메모리(`project-baseline-*`) 대비 1.5배 이상 급증이면
   원인을 규명한다. 단, 기준선 자체가 stale일 수 있다(실제로 그랬다 — 89ms는 1200s
   전장에 물리적으로 불가한 값이었다).
5. 메모리: MC 장시간 1회 RSS 추이 `[실측]` + frames 누적 · figure close 가드 코드 확인.
6. **하위호환** — 구버전 시나리오 cfg(과거 `enable_xxx` 누락 dict)로 로드·실행이 되는가.
7. **번들 과잉·무결성** — `spec` 의 `datas`·`hiddenimports` 완전성과, 반대 방향인
   *쓰지도 않는 대형 패키지*(2026-09-12 실측: dist 1.2GB 중 445MB가 미사용 torch·pyarrow).
8. **중단·외부 의존** — MC 중단(abort) 후 워커 잔존·풀 정리 · Cesium CDN이 끊겨도
   graceful 한가. 둘 다 *정상 경로에서는 안 보이는* 자리다.

## 3. 발견 대장 (`FINDINGS.md`) — 정본

### 3.1 진입 기준

- 개별 등재는 **`중간` 이상만.**
- `낮음`은 집계 한 줄로: *"매직넘버 47곳(부록)"*, *"`encoding=` 누락 12곳"*.
- 대장 본문은 **30~50개를 넘기지 않는다.** 넘으면 묶거나 뿌리로 통합한다.
- 부록 목록은 문서에 박지 말고 **재생성 스크립트**를 `analysis/probes/`에 남긴다.

> 발견 300개 표는 목록이 아니라 쓰레기통이다.

### 3.2 항목 형식 (검사 스크립트가 파싱한다 — 형식 변경 금지)

```markdown
### F-001 · 축: 모델타당성 · 상태: 미처리
- 위치: engine_combat.py:3421 `if pk_base * ecm_factor > rand():`
- 근거: [코드]
- 이력: [신규]
- 심각도: 중간
- 반증조건: 이 판단이 틀리려면 무엇이 참이어야 하는가
- 재현: (없음) 또는 analysis/probes/p001_xxx.py
- 수정비용: 소
- 회귀위험: 골든 영향 없음
- 실행주체: 나 단독
- 뿌리: 증상
- 요약: 한 줄
- 근거본문: (자세한 논증)
```

- `상태`: `미처리` / `수정됨` / `오탐` / `기각(사유)`
- `심각도`: `치명` / `높음` / `중간`
- `수정비용`: `소` / `중` / `대`
- `실행주체`: `나 단독` / `사용자 결정 필요` / `실측·승인 필요`
- `뿌리`: `증상` / `독립` / `F-007,F-012 의 뿌리`

### 3.3 칼럼의 의미

| 칼럼 | 무엇을 적나 |
|------|-------------|
| **심각도** | 안 고치면 **무엇이 언제** 깨지나. 막연한 '위험' 금지 |
| **수정비용** | 라인수·건드릴 파일 수 (소/중/대) |
| **회귀위험** | 고치다 무엇을 깨뜨릴 수 있나. **골든 갱신이 필요한가** |
| **실행주체** | 나 단독 / 사용자 결정 필요 / 실측·승인 필요 |
| **뿌리** | 이 발견이 다른 발견 몇 개의 뿌리인가 (연결 ID) |
| **상태** | 미처리 / 수정됨 / 오탐 / 기각(사유 필수) |

> **회귀위험**이 이 프로젝트에선 특히 크다. 골든 **42케이스 × 32지표**가 걸려 있어
> "고쳤더니 골든이 바뀌는" 수정은 비용이 몇 배다.
> (규모는 pre-commit 게이트 출력에서 실측. `CLAUDE.md`는 8케이스·38×29 등으로
> 적고 있어 stale — 0단계에서 확인할 것.)

### 3.4 심각도 상한 규칙 (인플레 방지)

- `치명` · `높음` 은 **실제로 재현한 실패가 있을 때만** 부여 가능 `[실측]`.
- 재현 못 했으면 논증이 아무리 그럴듯해도 **최대 `중간`.**
- **반증조건**을 한 줄 적는다. 그 조건을 확인 안 했으면 등급을 올리지 않는다.
  - 예: *"호출처 0 → 죽은 코드"* 의 반증 조건은 `getattr` · 동적 디스패치.
    이 프로젝트는 실제로 `getattr(app_main, ...)`을 쓴다.

### 3.5 발견 검증

- `치명`/`높음`으로 분류한 발견은 전부 **실제로 그렇게 되는지 재현**한다.
- 재현 스크립트를 `analysis/probes/`에 남긴다(다음에 또 쓰게).
- 재현 안 되면 심각도를 낮추거나 `오탐`으로 기록한다. **지우지 않는다** —
  같은 오탐을 다음에 또 발견하지 않게.

### 3.6 기각 기록

- 기각한 발견은 지우지 말고 상태를 `기각`으로 두고 **사유**를 적는다:
  `의도적 단순화` / `비용 대비 이득 없음` / `이미 음성 결론` / `오탐`
- "안 고치기로 함"도 결론이다. 사유 없이 지우면 다음 분석이 재발견한다.

## 4. 우선순위 — 심각도순은 틀린 순서다

두 가지 이유로 단순 심각도 정렬은 실패한다.

- **의존 관계**: A를 고치면 B가 저절로 사라지거나, B를 먼저 해야 A가 가능하다.
- **동일 지점**: 같은 파일·함수를 건드리는 발견을 따로 처리하면 그 파일을 다섯 번 연다.

### 4.1 순서 잡기 절차

1. 발견 간 의존을 그린다: `A를 고치면 B 소멸` / `B 선행 필요` / `독립`.
2. 같은 파일·함수를 건드리는 발견을 **묶음(batch)** 으로 합친다.
3. 순서는 **의존 → 묶음 → 심각도 → 회귀위험 낮은 순.**
4. 결과: `1차 묶음 ~ N차 묶음` 작업 계획. **각 묶음에 완료 판정 기준**을 적는다
   ("개선한다"가 아니라 "무엇이 무엇으로 바뀌면 끝인가").

### 4.2 회피 경보 — 나는 쉬운 걸 고르고 무서운 걸 미룬다

매직넘버 47곳 정리는 명확하고 안전해서 올리기 쉽고, 구조적 뿌리 문제는 크고
회귀 위험이 커서 "나중"으로 밀게 된다. **목록은 그럴듯한데 정작 중요한 게 안 고쳐진다.**

- 뿌리가 **3개 이상**을 설명하면 증상들보다 **무조건 위로** 올린다.
- 최종 우선순위 **상위 5개 중 최소 2개는 구조적**이어야 한다.
  전부 국소 수정이면 내가 회피한 것이다 — 그렇게 됐으면 **이유를 명시**한다.
- 회귀 위험이 크다는 이유로 미룬 항목은 `보류`가 아니라 **선행 작업이 무엇인지**를 적는다.
  미루는 게 아니라 순서를 매기는 것이다.

### 4.3 로드맵 충돌

`plan_roadmap.md`에 이미 정해진 우선순위(v22 1순위 등)와 분석 결론이 다를 수 있다.

- 계획을 **조용히 덮어쓰지 않는다.**
- `기존 계획` / `분석 결론` / `왜 다른가` 를 나란히 놓고 **사용자 판단을 요청**한다.
- 기존 계획이 맞다고 판명되면 그 근거를 대장에 남긴다(같은 제안 반복 방지).

### 4.4 결정 요청 일괄화

`사용자 결정 필요` 가 20개 쌓이면 실제로는 아무것도 못 고친다.

- 분석 중에 하나씩 묻지 않는다. **모아 둔다.**
- 분석 종료 시 한 번에 제시 — 각 항목에 `내 추천 + 근거 + 안 정하면 무엇이 막히나`.
- 결정 안 나도 **진행 가능한 항목부터 먼저** 고친다. 대기로 멈추지 않는다.

### 4.5 도메인 판단은 내 몫이 아니다

"이 단순화가 타당한가"는 만든 사람만 아는 게 섞여 있다.
(예: *적 편대에 정밀무기 1발 편성* 이 비현실인가, 의도적 최소 시나리오인가)

- 코드가 **틀린 것인지 의도적 단순화인지** 내가 판단 못 하는 항목은
  별도 절에 **질문 형태**로 모은다. **임의로 버그라 단정하지 않는다.**

## 6. 규약 강제 — 문서가 아니라 도구로

지금까지의 규칙은 전부 **내가 스스로 지켜야 하는 것**이다. 판 중간에 컨텍스트가 차면
근거 등급을 빼먹고, `[추정]`을 슬쩍 결론에 올리고, 커버리지를 낙관적으로 적을 수 있다.
사용자가 그걸 알아챌 방법이 없다.

→ **`analysis/check_protocol.py`가 이를 기계로 검사한다.**

### 6.1 검사 항목

1. `FINDINGS.md`의 모든 항목에 **근거등급 태그**가 있는가
2. `[실측]` 주장에 **명령어와 출력 블록**이 실제로 딸려 있는가
3. `치명`/`높음` 인데 **재현 근거가 없는** 항목이 있는가 (3.4 위반)
4. 인용한 **파일:라인이 실제로 존재**하고 **앵커 텍스트가 그 줄에 있는가**
5. `COVERAGE.md`의 파일 목록이 **실제 폴더와 일치**하는가 (누락·유령)
6. 상위 5개 발견 중 **구조적 항목이 2개 미만**인가 (4.2 회피 경보)
7. 대장 본문이 **50개를 넘는가** (3.1 위반)
8. `기각` 상태인데 **사유가 없는** 항목 (3.6 위반)

### 6.2 운영 규칙

- **매 판 끝에 실행하고 출력을 그대로 붙인다.** FAIL이면 **그 판은 끝난 게 아니다.**
- 이 스크립트는 **분석을 시작하기 전에** 만들어 커밋했다.
  발견이 나온 뒤에 검사기를 고치지 않는다.
- 검사기를 수정해야 하면 **이유를 커밋 메시지에** 남긴다
  (*검사가 틀렸다* 인지 *통과하기 어려워서* 인지 드러나게).
- `python analysis/check_protocol.py --selftest` — 일부러 위반한 가짜 항목을 넣어
  검사기가 잡는지 확인한다 `[실측]`. **통과는 증거가 아니다.**

### 7.1 COVERAGE.md

- 모든 파일을 `전체읽음` / `발췌` / `안봄` 으로 기록. **누적**이며 덮어쓰지 않는다.
- 최종 종합에서 **전체 코드 라인 중 실제로 읽은 비율**을 실측으로 낸다.
- `안봄` 으로 남은 파일은 **숨기지 않는다.** 왜 남았는지 적는다.

### 7.2 행동 연결 — 문서로 끝나면 실패다

100쪽 분석서를 만들고 아무것도 안 고치는 것이 가장 흔한 실패다.

## 9. B단계 — 수정 단계 설계

### 9.0 B단계가 A에 추가하는 대장 필드

3.2의 **필수 필드 집합은 바꾸지 않는다.** B에서만 쓰는 **선택 필드** 셋을 더한다:

```markdown
- 대상: engine_combat.py, engine_core.py        <- 9.3 착수 선언 (파일 3개 이하)
- 짝: 회피 기동(enable_ship_evasion) ON 이어야 발현  <- 필수. 없으면 '없음(이유)'
- 무대: 드론 없는 포화 편성, 20~40km             <- 필수. 수치로 특정할 것
- 예측: 기준 시나리오 고정 seed 요격률 ↑ 최소 3%p  <- 9.2 R형식일 때만
- 결과: (수정 후 실측값 + 예측 부합/불일치 판정)
```

### 9.1 작업 단위 = 묶음

- **한 묶음 = 커밋 2개.** 9.2가 예측·선언을 코드보다 먼저 커밋하라고 요구하므로
  *"한 묶음 = 한 커밋"* 은 성립하지 않는다(모의 실행에서 드러난 모순, 2026-09-20):
  1. **선언 커밋** — 문서만(`대상`·`짝`·`무대`·`예측`). 버전 번호 없음.
  2. **묶음 커밋** — 코드 + 대장 상태·결과. 제목에 **발견 ID(`F-0NN`)를 반드시** 넣는다.
     검사기가 이 ID로 '이 묶음의 코드 커밋'을 식별해 선행성을 판정한다(9.8과 맞물림).
- (해당되면) 묶음 커밋에 버전 번호 하나.
- 묶음 경계 조건 세 개를 **동시에** 만족해야 한다:
  1. 같은 파일·함수를 건드린다
  2. 회귀 영향이 같다 (골든이 같이 움직이거나, 같이 안 움직인다)
  3. **독립적으로 되돌릴 수 있다**
- 상한: **3개 파일 또는 200라인.** 넘으면 쪼갠다 — 실패 시 원인 분리가 안 된다.
  - 라인 상한은 **코드 변경에만** 적용한다. `analysis/` 산출물과 `*.md` 문서는 제외 —
    분석 판의 산출물이고 회귀 위험의 종류가 다르다. **도구(`audit_*`)는 제외하지 않는다** —
    그것도 고치면 깨질 수 있는 코드다. (검사기 `is_code()`가 같은 정의를 쓴다.)

### 9.2 착수 게이트 — 실패할 수 있는 판정을 먼저 만든다

**B의 핵심.** "고쳤다"를 증명하려면 "고치기 전엔 실패했다"가 먼저 있어야 한다.

> 1차 초안은 이걸 **실행 프로브**로만 봤고, 그래서 프로브화가 불가능한 발견에서
> 게이트가 통째로 죽었다(약점 가). 착각의 원인은 이것이다 —
> **프로브의 본질은 코드가 아니라 "미리 정한, 실패할 수 있는 판정"이다.**
> 형식은 셋이고, 발견의 성격이 어느 것을 쓸지 정한다.

| 형식 | 쓰는 경우 | 기준선이 되는 것 |
|------|-----------|------------------|
| **P · 실행 프로브** | 관찰 가능한 오동작 (기본) | 지금 **실패하는** 스크립트 `analysis/probes/pNNN_*.py` |
| **S · 정적 불변식** | 구조·계층 위반·죽은 코드·위생·stale 문서 | `audit_static_scan.py`(또는 `audit_property.py`)에 **먼저 추가**해 지금 **FAIL 나는** 검사 함수 |
| **R · 사전등록 예측** | 정답이 없는 것 — 모델 가정·근사의 타당성 | 코드를 건드리기 **전에** 대장에 박은 `예측:` 줄 |

- **계층 위반·죽은 코드는 프로브 불가가 아니다 — S로 내려온다.** 원리적으로
  실패하는 판정을 못 만드는 건 **모델 타당성 부류뿐**이고, 거기에만 R을 쓴다.
- S를 택하면 **그 검사 함수가 영구 안전망으로 남는다**(7.2). 같은 것을 두 번 발견하지 않는다.

**R의 규칙** — 느슨한 예측은 예측이 아니다:

1. 예측에 **지표명 + 방향 + 최소 크기 + 측정 시나리오**를 전부 적는다.
   - ❌ *"요격률이 변한다"* (무엇이 나와도 맞는 말 = 실패 불가능 = 판정이 아니다)
   - ✅ *"기준 시나리오 MC 200회 요격률이 오른다, 최소 +2%p"*
2. 예측은 **코드를 건드리기 전에 문서만 커밋**한다. 커밋 이력이 사후 조작을 막는다.
3. **외부 앵커 1개 이상**(공개 제원·문헌·교리, URL 필수). 못 달면 `[미확인]`이고,
   그러면 **고치지 않는다** — 4.4 결정 요청으로 올린다(도메인 판단은 내 몫이 아니다, 4.5).
4. 측정이 예측과 **어긋나도 그것이 결과다.** 되돌리는 것이 기본이되 사유와 함께
   사용자 결정으로 올린다. **예측을 나중에 고쳐 쓰지 않는다.**
5. **ON/OFF가 bit-identical이면 그 수정은 아무 일도 안 한 것이다**(죽은 수정).
   v20.5의 죽은 기능 부채가 정확히 이 경로로 태어났다.

**짝·무대 — 형식과 무관하게 전 항목 필수** (역사 대조에서 되살린 것)

이 저장소의 발현 증거 3종(발현 델타·**짝 기능**·**발현 무대**) 중 2차 설계는 델타만
가져왔다. 역사 대조에서 **짝·무대가 없으면 못 잡는 실제 사건이 3건** 나왔다:

| 필드 | 묻는 것 | 이게 없어서 생긴 실제 사건 |
|------|---------|---------------------------|
| `짝:` | 이 수정이 성립하려면 **무엇이 함께 참이어야/바뀌어야** 하는가 | 레이더 침묵은 **회피 기동이 OFF면 죽는다**(함대 정지→조준 좌표 이격 0) · 자폭 집계는 **분모만 고치니 지표가 더 거짓말**(`be4e8b9`) |
| `무대:` | **어떤 편성·거리·조건에서 발동**하는가 (수치로) | 레이저는 드론이 5km에 와야 하는데 **함포가 23km에서 다 잡는다**(v17.2 음성) |

> **"한쪽만 고치는 게 안 고치는 것보다 나쁠 수 있다."** 짝을 못 적겠으면 그건
> 묶음 경계가 틀린 것이다(9.1로 돌아가 합치거나 쪼갠다).

**판정은 실재해야 하고, 노이즈와 구분돼야 한다**

- P는 **프로브 파일이 실제로 있어야** 하고, S는 **`chk_` 함수가 감사 도구에 실제로
  정의**돼 있어야 한다. 경로·이름만 적어 두는 것은 판정이 아니다(검사기가 대조한다).
- R의 예측 크기는 **노이즈보다 커야 판정이 된다.** 기준 시나리오 요격률의 시드 산포는
  **±4.0%p**다 — MC로 "+2%p"를 예측하면 무엇이 나와도 설명된다.
  → **고정 seed 결정론 대조가 기본**이다(`audit_effect.py`가 `sim_seed=7`로 그렇게 한다).
  확률 경로를 쓸 거면 **표본수와 산포를 함께** 적는다.

**착수 절차 (형식 무관 공통)**

```
1. 변경 전 pre-commit 게이트를 먼저 돌려 PASS 확인 [실측]
   -> 변경 후 FAIL이 나면 그게 내 수정 탓임이 확정된다.
2. 그 발견의 판정(P/S/R)을 만들고, '지금은 실패한다'를 확인 [실측]
   -> R은 실행이 아니라 '예측 커밋'이 이 단계다.
3. 판정 없이 코드를 건드리지 않는다.
```

### 9.3 수정 중 — 범위 확대는 기계로 막는다

- **한 번에 한 묶음.** 동시 진행 금지 — 실패 시 원인을 못 가른다.
- 대장 상태를 `수정중`으로(세션이 끊겨도 재개 지점).
- **착수 선언**: 9.2의 예측 커밋과 같은 커밋에 `대상:` 파일 목록(3개 이하)을 박는다.
- 커밋 직전 검사(기계): `git diff --name-only`가 `대상:`의 **부분집합**인가 ·
  `--numstat` 합이 **200라인 이하**인가. 아니면 FAIL.
  → 범위를 넓히려면 **선언을 고쳐 다시 커밋**해야 하므로 이력에 드러난다.
  **조용한 확대가 불가능해지는 것이 요점**이다(약점 다: 문서 규칙으론 안 막힌다).
- **B판 안에서 선언 없이 코드를 고치면 FAIL**(반경 E/C/W/U/B). 대장에 안 올리고
  그냥 고치는 우회로를 막는다. 도구·문서 반경은 경고.
- **코드를 고치면 다른 발견의 인용 라인이 밀린다.** 하루에 네 번 손으로 고친 뒤
  `analysis/refresh_anchors.py` 로 도구화했다 — **제안만** 하고, 앵커 텍스트가 사라졌거나
  후보가 여럿이면 `[판단 필요]`·`[모호]` 로 표시만 한다(1.2 의 *"자동 갱신하지 않는다"* 준수).
  묶음을 닫기 전에 `python analysis/refresh_anchors.py` → 확인 → `--apply`.
- **수정 중인 항목의 앵커는 안 맞는 게 정상**이다(그 줄을 일부러 바꿨으므로).
  검사기는 `수정중`/`수정됨` 항목의 앵커 불일치를 경고로만 낸다 — FAIL 이면 B단계의
  **모든 수정이 커밋 불가**가 된다(모의 실행에서 실제로 막혔다). 묶음을 닫을 때
  위치·앵커를 **새 코드로 갱신**한다.
- 고치다 보이는 다른 것은 9.6으로.

### 9.4 수정 후 검증 — 영향 반경이 목록을 정한다

> 1차 초안은 회귀 골든에만 기댔다(약점 나). **회귀 PASS는 "안 깨뜨렸다"의 증거가 아니다** —
> 골든은 **엔진 출력 42케이스 × 32지표**이고, 워커·UI·exe·번들·성능·메모리·도구 자신은
> 보지 않는다. 그렇다고 매번 전부 돌리면 라(비용)에 걸린다.
> → **검증 선택을 사람 판단에서 뺏는다.** `git diff --name-only`를 아래 표에 기계로
> 매핑해 필수 검증을 뽑는다. *"UI만 건드렸으니 회귀 생략"* 같은 낙관을 못 하게.

**이 저장소엔 이미 2층 안전망이 있다** `[실측 2026-09-20]`:

**검증 3단**

```
① 판정 재실행 -> 실패->통과 전환 확인 [실측]. 출력을 그대로 붙인다.
   (R은 '예측 지표를 측정' 이 이 단계다)
② 반경 표가 지정한 검증 전부 [실측]
③ 골든이 바뀌었으면:
   바뀐 지표를 '어느 것이 왜 얼마나' 하나씩 설명할 수 있어야 한다.
   설명 못 하는 지표가 하나라도 있으면 --update 금지. 그건 의도 밖 변화다.
④ 골든이 '하나도' 안 바뀌었으면 (반경 E·C 인데):
   그건 안전한 게 아니라 '무대가 없다'는 신호다. 왜 안 움직였는지 규명한다 —
   골든 42케이스에 발현 조건이 없는가 / 짝 기능이 OFF 인가 / 게이트 버그인가.
   규명 못 하면 그 수정은 죽은 수정이다(레이저 v17.2 가 그 자리였다).
```

> ③이 관건이다. *"의도된 변경이면 `--update`"* 는 너무 느슨하다 —
> 의도한 변경 **옆에** 딸려온 변화를 통째로 승인해 버린다.
> **④는 그 반대쪽 사각이다.** 2차 설계는 "골든이 안 바뀌면 안전"으로 읽혔는데,
> 엔진을 고쳤는데 42케이스 중 하나도 안 움직였다면 **고친 게 아무 데서도 안 나타난다**는 뜻이다.

**남는 사각을 명시한다.** 묶음 완료 보고에 한 줄:
*"골든이 안 보는 영역 X → Y로 확인 → 그래도 남는 사각 Z."*
**사각 0이라고 주장하지 않는다.** 그리고 반복 점검이 가능한 것은 그 자리에서
`audit_static_scan.py`·`audit_property.py`에 **검사 함수로 굳힌다**(7.2) —
B단계의 부산물로 **골든 밖 안전망이 자라는 것**이 약점 나에 대한 누적 답이다.

### 9.5 게이트 비용 — 무엇을 매번 돌리고 무엇을 아끼나

`[실측]`으로 다시 잰 결과 1차 초안의 *"게이트 실측 2분+"* 는 **과대였다**(실제 41.2초).

- **pre-commit(41초)은 묶음마다 돈다. 생략 금지** — 이 가격에 아낄 이유가 없다.
- **pre-push는 181초** `[실측 2026-09-20]`. 묶음마다 푸시하면 묶음당 3분이 더 붙는다.
  → **묶음마다 커밋, 푸시는 2~3묶음 묶어서**(또는 세션 매듭). 9.9의 *"묶음마다 푸시"* 는
  이 수치를 모르고 쓴 것이라 여기서 정정한다.
  단 **반경 E·C 를 건드린 묶음은 그 자리에서 푸시**한다 — `audit_property`(133s)가
  엔진 불변식의 제2 오라클이라, 미루면 어느 묶음이 깼는지 못 가른다.
- **무거운 것**(전체 빌드 약 182s + exe 스모크)은 **반경 B일 때만** + 세션 매듭 1회.
- 비용을 줄이는 방법은 "게이트를 건너뛰는 것"이 아니라 **반경을 좁게 유지하는 것**이다(9.1 상한).

### 9.6 수정이 새 발견을 낳으면

- **그 자리에서 고치지 않는다.** 대장에 새 ID로 등재하고 현재 묶음을 먼저 닫는다.
- 예외: 그 발견 때문에 현재 수정이 **완성 불가능**한 경우
  → 묶음을 합치고 `대상:` 선언을 고쳐 커밋(9.3), 그 사실을 기록.

### 9.7 실패 시

- 커밋 전이면 `git restore`, 커밋 후면 `revert`. **묶음 단위로** 되돌린다.
- **2회 시도해서 안 되면 중단**하고 대장에 `보류(사유)` + 무엇이 막았는지.
- 되돌린 것도 **기록**한다 — 같은 접근을 다시 시도하지 않게(막다른길 규칙).
- R의 예측이 빗나가서 되돌린 경우는 **음성 결과로 메모리에 남긴다.**

### 9.8 버전 번호·changelog 귀속

기준은 하나다 — **exe 사용자가 체감하는 변화가 있는가.**

| | 처리 |
|---|---|
| 체감 변화 **있음** | `vX.YY.ZZ` 부여 + changelog 1건. 유형은 버그·수치 정정이면 `수정`, 없던 동작이 생기면 `추가`. **죽은 코드 제거는 `수정`** (`삭제`는 기능 자체를 없앨 때만) |
| 체감 변화 **없음** (도구·분석 문서·내부 리팩터) | 버전 번호 **없이** 커밋 제목 `분석 F-0NN: 요약 (문서만 / 도구만)` |

이건 새 규칙이 아니라 이 저장소의 기존 실무와 같다
`[실측: git log — c8c47e0 "분석 규약 확정 … (문서만)" 는 버전 번호가 없다]`.

### 9.9 진행 추적·중단 대비

- **대장의 상태 필드가 진척 대시보드다.** 별도 진행 문서를 만들지 않는다(stale 원천).
- 묶음 하나 끝날 때마다: 커밋 → `SESSION_LOG` + `plan_roadmap` 갱신.
  **푸시는 9.5 규칙대로**(반경 E·C면 즉시, 아니면 2~3묶음 묶어서 — pre-push 181초).
- 미완 묶음은 워킹트리에 남되, `SESSION_LOG`에 **"무엇을 하다 말았나"** 를 적는다.

### 9.10 B단계 기계 검사 (`check_protocol.py --stage b`)

6.1의 A 검사에 더해:

1. 상태가 `수정중`/`수정됨` 인데 **P/S/R 어느 판정도 없는** 항목
2. **판정 실재** — P의 프로브 파일이 있는가 · S의 `chk_` 가 감사 도구에 정의돼 있는가
3. **짝·무대 선언**이 있는가 (무대에 수치가 없으면 경고)
4. `예측:` 이 **지표·방향·0이 아닌 크기·시나리오** 4요소를 갖췄는가
5. `예측:` 이 **노이즈와 구분 가능한가** — 고정 seed 또는 표본수+산포 명시
6. `예측:` 에 **외부 앵커 URL**이 있는가
7. **선행성** — 예측 도입 커밋에 코드가 없고, 그 커밋이 코드 커밋의 **조상**인가
   (사후 작성·예측 고쳐쓰기 차단)
8. `수정됨` 인데 `결과:` 와 **부합/불일치 판정**이 있는가
9. `대상:` 선언 대비 실제 diff **초과** · 파일 3개/200라인 상한 · **선언 없는 코드 변경**
10. diff의 모든 파일이 **반경 표에 분류되는가** — 미분류면 FAIL

**돌리는 것을 잊을 수 없게 `pre-commit` 훅에 배선했다**(0.27초 `[실측]`).
대장이 없으면 자동 생략하므로 **B판 밖의 평소 패치는 막지 않는다.**

> 이 검사기도 A와 같은 원칙으로 **B 작업을 시작하기 전에** 커밋한다.
> 발견이 나온 뒤에 검사기를 느슨하게 고치지 않는다. 고쳐야 하면 **이유를 커밋 메시지에.**

| 설계 | 점수 | 못 잡은 것 |
|------|------|-----------|

### 9.13 이 설계가 여전히 안고 있는 것 (정직하게)

- **내용 판단은 기계 밖이다.** `짝: 없음` · `무대: 적정 편성` · 무관한 URL은 형식을 통과한다.
  자폭 집계 사건이 ⚠로 남은 이유다. 완화책은 무대에 수치가 없으면 경고하는 것뿐.
- **R의 예측은 내가 쓴다** — 맞히기 쉬운 예측만 고르는 편향은 기계가 못 잡는다.
- **반경 표는 stale해진다.** 미분류 FAIL(변경분) + 저장소 전체 미분류 경고로 *새는 것*은
  막았고, 분류의 타당성(어느 반경이 맞나)은 사람 몫이다.
- ~~pre-push 비용 미확인~~ → **해소**(181초 실측, 9.5·9.9 정정).
- **`--no-verify`** 는 의도적 회피라 규약 범위 밖이다.
