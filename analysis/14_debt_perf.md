## 2. NaN/Inf · 0 나눗셈 `[실측]`

분모가 변수인 나눗셈 **151곳**(engine_* 6파일) → 0이 될 수 있는 형태(`len()`·`sum()`·
`n_*`·`*count*`·`*total*`)로 좁히니 **8곳**. 각각을 읽어 판정:

| 위치 | 판정 |
|------|------|
| `engine_airforce.py:349` `sum(zs)/len(SLOC_ZONES)` | ✅ 모듈 상수, 0 불가 |
| `engine_airforce.py:478` `…/len(self.ad_sites)` | ✅ `if self.ad_sites else 0.0` 가드 |
| `engine_airforce.py:485` `…/len(self.bases)` | ✅ `if self.bases else 0.0` 가드 |
| `engine_army.py:437` `…/len(self.sites)` | ✅ `if not self.sites: return 0.0` 선행 |
| `engine_campaign.py:285·720` `…/len(SLOC_ZONES)` | ✅ 모듈 상수 |
| `engine_combat.py:7293` `…/len(v)` | ✅ dict comprehension 에 `if v` |
| `engine_combat.py:7680` `…/n_ships` | ✅ `n_ships = len(ships) if ships else 1` |

**8/8 거짓양성. 0분모 결함 0건.** 이 프로젝트는 나눗셈마다 가드를 붙이는 습관이 잡혀 있다.
(`audit_property` 가 NaN/Inf 를 런타임으로도 감시한다 — 45케이스 위반 0.)

## 3. 성능 — 실측 병목이 추측과 다르다 `[실측]`

```
단발 1회(랴오닝 항모전단 · seed 7) — cProfile
  wall 1.34s (프로파일러 포함) · sim_time 1652s · 함수 호출 508만

  cumtime  ncalls    함수
  0.375      1653    _friendly_defense        28%
  0.292   1174130    _et_col.<locals>._get    22%   ← 프록시 속성 위임
  0.279      1653    _update_positions        21%
  0.145      1653    _friendly_strike
  0.137      1653    _enemy_fire
  0.117   1298792    builtins.getattr               (위 _get 이 부른 것)
```

**상위에 PNG substep 이 없다.** [[plan-v12-numpy]] 는 프로파일링 결과
*"PNG substep 이 진짜 병목"* 이라 판단했는데 지금은 아니다 — 병목이 옮겨갔거나
측정 시나리오가 다르다. 규약 2.4-4 가 요구한 *"추측한 병목과 실측 병목이 다르면
그 차이를 명시하라"* 에 해당하므로 명시한다.

**현재 2위는 v12.7 이행의 미완성 비용이다** → **F-014**.
`_et_col()` 은 *"데이터는 엔진 컬럼에, 객체는 (엔진, 행 i)만"* 이라는 단계1 호환 shim 이라
속성 접근 한 번이 `getattr` + 인덱싱이 된다. **단계2를 끝내면 사라지지만 지금은
값만 치르고 이득은 없다.**

> 프로파일러 오버헤드가 포함된 수치다(메모리 기준값은 단발 667ms). **순위**는 신뢰하되
> **절대 시간**은 그대로 인용하지 않는다 — 그래서 F-014 에 `높음` 을 주지 않았다.
